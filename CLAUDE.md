# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Стек и окружение

- **Unity 6000.3.11f1.** Автотестов в проекте нет, поэтому единственный способ убедиться, что изменение работает, — Play Mode. Не предлагай «прогнать тесты»: прогонять нечего. Play Mode и сборку можно запускать как из редактора, так и командами Unity CLI (см. раздел про управление редактором).
- **Сущности — собственная ECS-подобная система**, написанная под этот проект: `Assets/_Project/Develop/Runtime/Gameplay/EntitiesCore`. Это **не** Entitas и **не** Unity DOTS — не предлагай API, атрибуты и паттерны этих фреймворков.
- **DI — собственный контейнер** в `Runtime/Infrastructure`. Zenject, VContainer и прочие сторонние DI не используются.
- **Кодогенерация** — редакторский скрипт `Assets/_Project/Develop/Editor/EntityAPIGenerator.cs`, пункт меню `Tools → GenerateEntityAPI`. Он полностью перезаписывает единственный файл `EntitiesCore/Generated/EntityAPI.cs`.
- **Внешние зависимости**: DOTween (`Assets/Plugins/Demigiant`), Newtonsoft.Json через NuGetForUnity.
- **Assembly definitions для своего кода нет** — весь код проекта компилируется в `Assembly-CSharp`.

## Границы редактирования

- **Менять можно любые файлы проекта** — код, сцены, префабы, конфиги, настройки. Отдельного разрешения на сам факт правки не требуется.
- **Только в рамках запроса.** Правки делаются по поставленной задаче, а не по собственной инициативе: расширять объём работ за пределы того, о чём попросили, нельзя.
- **Заметные изменения согласовывай заранее.** Оценивай вес предстоящих правок сам: если они существенные — опиши, что именно собираешься поменять, и дождись подтверждения. Мелкие правки в рамках уже поставленной задачи выполняются без дополнительных вопросов.
- **Прицельные запреты имеют приоритет.** Если по какому-то файлу, папке или виду изменений дан явный запрет, он действует до отмены и перекрывает это общее разрешение.
- **Сцены, префабы и ассеты правь через редактор, а не текстом.** `.unity`, `.prefab`, `.asset` и `.meta` — это Unity-YAML, где связи держатся на GUID и fileID, и ручная текстовая правка легко рвёт ссылки. Корректный путь — команды Unity CLI к живому редактору (см. ниже); текстовое редактирование такого файла — крайняя мера, когда редактор недоступен.

## Управление редактором через Unity CLI

В проекте установлен пакет `com.unity.pipeline`, а в системе — Unity CLI (`%LOCALAPPDATA%\Unity\bin\unity.exe`). Вместе они позволяют управлять запущенным редактором из терминала: создавать и менять GameObject'ы, редактировать сцены и ассеты, читать иерархию, выполнять произвольный C#, входить в Play Mode и читать логи.

- **Перед правкой сцены, префаба или ассета выполняй `unity status`.** Если редактор подключён (состояние `ready`) — работай командами по живому проекту, а не патчем файла.
- **Скилл `unity-cli`** из официального плагина Unity описывает полный набор команд — обращайся к нему, а не угадывай синтаксис.
- **Safe Mode.** При ошибках компиляции C# редактор уходит в Safe Mode, пакет не загружается и связь пропадает. В этом случае чини ошибки компиляции, а не переходи к слепому редактированию файлов.
- **Если редактор не запущен**, команды управления недоступны — тогда либо попроси открыть проект, либо действуй в пределах кода.

## Где живёт код

`Assets/_Project/` — папка проекта со **всем пользовательским кодом и ресурсами**. Всё остальное под `Assets/` — это импортированные пакеты и плагины (`Plugins/Demigiant`, `Hovl Studio`, `TextMesh Pro`, `Packages/Newtonsoft.Json`, `Settings`, …); такое разделение нужно, чтобы свои ассеты не путались с пакетными. Подчёркивание в имени держит `_Project` наверху Project-окна — сохраняй его и в namespace.

```text
Assets/
  _Project/                     # Основная папка проекта
    ...                         # Графические и звуковые ассеты
    Develop/                    # Основной код (C#)
      Editor/                   # Редакторские скрипты
      Runtime/                  # Игровая логика
        Configs/                # Структура конфигов
        Gameplay/               # Геймлейная часть
          EntitiesCore/         # Своя ECS-подобная система сущностей (+ ООП)
            Generated/          # Вывод EntityAPIGenerator — руками не править
          Features/             # Геймплейные фичи, ИИ
          GameMode/             # Логика игрового режима
          Infrastructure/       # Точка входа, зависимости, игровой цикл
        Infrastructure/         # Точка входа в проект, DI контейнер
        Meta/                   # Главное меню, уровни, прогрессия
        UI/                     # MVP-модули интерфейса: Presenters, Views, Popups
        Utilities/              # Переиспользуемый слой, не знающий про игру
    Prefabs/                    # Префабы
    Resources/                  # Динамически загружаемые ресурсы
    Scenes/                     # Сцены
  ...                           # Сторонние ассеты, плагины, пакеты, другие настройки
```

**Параллелизм `Gameplay/` и `Meta/`** — это два домена игры одного уровня. Оба следуют одной схеме: подпапка `Infrastructure/` для бутстрапов/инсталлеров своей сцены и подпапка `Features/` для разбиения на фичи. Когда в игре появятся мета-механики (валюты, прогрессия, баттл-пассы) — их фичи кладём в `Meta/Features/`, по тому же шаблону, что и геймплейные. Не смешиваем мета-логику в `Gameplay/Features/` и наоборот.

## Архитектурные инварианты

Нарушение любого из этих пунктов — не вопрос вкуса, а поломка схемы, на которой держится проект.

### Сущности, компоненты, системы

- **Сущность — это набор компонентов плюс собственный список систем.** Глобальных циклов «система обходит все сущности» в проекте нет: каждая сущность гоняет свои инстансы систем, созданные для неё фабрикой. Поэтому система хранит состояние одной конкретной сущности — не делай её статической и не переиспользуй один инстанс на несколько сущностей.
- **Компонент — только данные.** Ровно одно публичное поле с именем `Value`, никакой логики и никаких методов. Роль компонента задаётся типом поля: `ReactiveVariable<T>` — состояние, `ReactiveEvent` — сигнал, `ICompositeCondition` — вычисляемое условие.
- **Словарь имён компонентов**: `…Request` — просьба что-то сделать, `…Event` — факт, что что-то произошло, `In…` — флаг текущей фазы (`InAttackProcess`), `Can…` и `Must…` — условие.
- **Доступ к компонентам — только через сгенерированный API** (`entity.MoveSpeed`, `entity.AddMoveSpeed(…)`). Ручной `entity.GetComponent<T>()` в геймплейном коде не пишем. После добавления нового компонента нужно перегенерировать API: `Tools → GenerateEntityAPI`.
- **Система кеширует ссылки на компоненты в `OnInit(entity)`** и дальше работает по своим полям. `OnUpdate(deltaTime)` сущность уже не получает — искать компоненты в апдейте невозможно и не нужно.
- **Системы не знают друг о друге.** Единственный канал связи между ними — компоненты сущности: одна система выставляет `ReactiveEvent` или меняет `ReactiveVariable`, другая на это реагирует. Прямые ссылки между системами не заводим.
- **Порядок `AddSystem` в фабрике — это порядок выполнения в кадре.** Перестановка строк меняет поведение, это не косметика.

### Граница с Unity

- **Unity-объекты попадают в сущность только через `MonoEntityRegistrator`** на префабе. Это единственное место в геймплейном коде, где делается `GetComponent`.
- **Система может читать и писать Unity-объект, но только тот, что пришёл к ней компонентом от регистратора** (`entity.Rigidbody`, `entity.Transform`). `GetComponent`, `Find`, `FindObjectOfType` и обращение к чужим `GameObject` из систем запрещены.
- **`EntityView` — только отображение.** Подписался на реактивные компоненты в `OnEntityStartedWork`, отписался в `Cleanup`. View не меняет геймплейное состояние и не вызывает системы.
- **`MonoEntity` на корне префаба** связывает сущность с объектом: собирает регистраторы, вью и коллайдеры.

### Система или сервис

Внутри `Features/` соседствуют оба вида классов, выбор — по владению состоянием:

- **Система** — если логика работает над компонентами одной конкретной сущности и живёт ровно столько же, сколько она. Создаётся фабрикой и добавляется в сущность.
- **Сервис** — если состояние общее для сцены или работа идёт над множеством сущностей сразу (`TowersPlaceholdersService`, `PlayerInteractsService`, `AreaEntitiesDetectorService`). Регистрируется в DI.

### Зависимости и DI

- **Контейнеры иерархические**: проектный живёт всю сессию, сценовый пересоздаётся при каждом переходе. Всё зарегистрированное — синглтон в своём контейнере.
- **Зависимости объявляются явным списком в конструкторе** — по сигнатуре должно быть видно, от чего класс зависит.
- **`DIContainer` внутрь класса передаётся только как исключение** — фабрикам, которые собирают объекты с заранее неизвестным набором зависимостей (`EntitiesFactory`). Во всём остальном коде контейнер виден только в `*ContextRegistrations`.
- **Все регистрации сцены — в `*ContextRegistrations.Process`.** `.NonLazy()` ставится тому, что должно быть создано сразу, а не по первому обращению.
- **`IInitializable` и `IDisposable`** на зарегистрированном объекте вызывает сам контейнер — вручную их дёргать не нужно.

### Жизненный цикл сцены

- **Сцена поднимается наследником `SceneBootstrap`** в три шага: `ProcessRegistrations` (регистрации) → `Initialize` (корутина, асинхронная подготовка) → `Run` (старт).
- **На сцене ровно один `Update`** — у бутстрапа, и он вручную тикает контексты в фиксированном порядке. Если новой вещи нужен апдейт, её место в этом порядке выбирается осознанно; отдельный `MonoBehaviour.Update` для геймплейной логики не заводим.
- **Сущности освобождаются отложенно**: `EntitiesLifeContext.Release(entity)` ставит в очередь, фактическое удаление происходит после прохода `Update`. Удалять сущность посреди итерации нельзя.

### UI

- **MVP**: презентер не наследует `MonoBehaviour`, получает вью и сервисы через конструктор, подписывается в `Initialize` и освобождает подписки в `Dispose`.
- **View не знает про сервисы и игровую логику** — только про свои UI-элементы, наружу отдаёт события.
- **Презентеры создаются фабрикой презентеров своей сцены**, попапы открываются через `PopupService`.

### Что считается Utilities

В `Utilities/` лежит только то, что ничего не знает про эту игру: `Reactive`, `Conditions`, `StateMachineCore`, `DataManagment`, `SceneManagment`. Критерий — код переехал бы в другой проект без правок. Как только появляется доменное понятие (башня, враг, волна, стадия), это уже `Features/` соответствующего домена.
